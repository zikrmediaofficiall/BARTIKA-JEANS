# حالة التنفيذ والفجوات — BARTIKA JEANS

آخر مراجعة للفرع الافتراضي `main` قبل بدء هذا الفرع.

## الموجود في الشيفرة
- Next.js 15 + TypeScript + React 19 + Tailwind.
- Supabase SSR/Auth/Postgres وRLS.
- ملفات SQL من 0001 إلى 0006.
- واجهات أولية: الصفحة الرئيسية، تسجيل الدخول، POS، المنتجات، المخزون، المشتريات، الجرد، الفواتير، العملاء، الخزينة، الموظفون، التقارير، الإعدادات، الاستبدال (قد تكون متفاوتة الاكتمال).
- PWA cache shell وصفحة Offline ثابتة.
- اختبارات حسابية أولية وGitHub Actions.

## قيود مثبتة من ملفات المشروع
- README يصرح أن Offline يقتصر على الغلاف الثابت وصفحة Offline؛ اعتماد البيع يتطلب اتصالًا بالخادم.
- ROADMAP يسجل الاستبدال الكامل، audit logs الشامل، تقارير الربح، مزامنة Offline، واختبارات الأجهزة على أنها غير مكتملة.
- migration 0001 يعرف app_role بالقيمتين admin وseller فقط.
- migration 0001 يقيد max_discount_percent بين 0 و20، وRPC البيع يرفض الخصم الأعلى من 20.
- واجهة shell تعرض اسم الدور بخيارين فقط (مدير النظام/بائع).
- الشعار الموجود في public/bartika-logo.svg بديل تصميمي مؤقت حسب ROADMAP؛ يلزم استبداله بالأصل المرخص المرفوع.
- المشروع لم يتم إثبات ربطه بقاعدة Supabase فعلية أو نجاح تطبيق جميع migrations أو اختبار RLS بأدوار حقيقية.

## قرارات ممنوع تجاوزها
- لا تفعّل بيع Offline قبل بناء مزامنة idempotent واختبارات مخزون متزامن.
- لا تُخزن أسرارًا أو كلمات مرور أو بيانات عملاء في المستودع.
- لا تعتبر فتح رابط InstaPay إثبات تحصيل.
- لا تضع تكلفة المنتج أو سعر الجملة أو الأرباح ضمن استعلام/استجابة Seller.
- لا تمنح Manager صلاحيات افتراضية أوسع من تفويض Admin.
- لا تعد المستخدم باستحالة الحذف المادي؛ استخدم ضوابط التلاعب والكشف والاستعادة.
- لا تدّعِ أن قاعدة محلية على لابتوب مغلق تستطيع استقبال طلبات متجر عام.
- لا تطبق migrations على مشروع إنتاجي غير معروف أو دون نسخة احتياطية وموافقة صريحة.

## بوابات القبول
1. Database/RLS: اختبار roles and permissions وتغطية جميع الجداول والـ RPC.
2. Inventory: اختبار معاملات بيع متزامنة على آخر وحدة؛ يجب ألا يصبح الرصيد سالبًا أو تتكرر الحركة.
3. Payments: مجموع الدفعات يطابق الفاتورة أو يظل المتبقي مسجلًا بوضوح.
4. Audit: كل تعديل حرج يسجل actor + before/after + correlation id.
5. Offline: إيقاف الشبكة، تنفيذ عمليات مسموحة، إعادة التشغيل، المزامنة، ثم إثبات عدم فقد/تكرار.
6. Backup: استعادة على قاعدة/جهاز نظيف والتحقق من العلاقات والأرقام.
7. UX: اختبار POS على جهاز لمس وطابعة وماسح باركود فعلي.
8. CI: lint, typecheck, unit tests, integration tests, build كلها ناجحة.
9. Release: نشر تجريبي ثم قبول المستخدم؛ لا إطلاق تجاري قبل موافقة Admin.

## القرارات المعمارية التي ما زالت تحتاج قرارًا قبل التنفيذ
- أين سيستضاف المتجر العام عندما يكون اللابتوب مغلقًا أو غير متصل؟
- هل تُسمح خدمة عامة محدودة للكتالوج والطلبات فقط، أم يصر المالك على أن يعمل المتجر عبر اللابتوب المحلي؟
- سياسة البيع Offline عند انفصال الأجهزة عن الخادم الرئيسي (حد بيع محلي/حجز مخزون مسبق/بيع محدود).
- تفاصيل عمولة الموظف: على إجمالي البيع أم صافي البيع المحصل بعد خصومات ومرتجعات؟
- صيغة رقمية وتفاصيل شعار أصلية قابلة للاستخدام في واجهة الموقع والطباعة.
