## 4. الخدمات الخارجية

### Vercel

- مشروع مستقل متصل بمستودع BARTIKA وفرع `main`.
- الدومين الأساسي مربوط بآخر Production.
- Production build وGitHub Actions نجحا على آخر Commit.
- متغيرات Supabase العامة ومفاتيح الخادم موجودة في Production.
- تمت إضافة `CLOUDINARY_CLOUD_NAME=lnsnp6km` إلى Production وPreview وDevelopment.
- لم تُضف بعد `CLOUDINARY_API_KEY` أو `CLOUDINARY_API_SECRET` أو `CLOUDINARY_FOLDER_MODE`.
- لا توجد Runtime errors في آخر نافذة فحص 30 دقيقة. أخطاء `x-action-redirect` التي ظهرت سابقًا كانت على Deployment قديم قبل إصلاح ترميز رسالة الخطأ العربية.

- مجلدات BARTIKA: `bartika-jeans/products`, `bartika-jeans/inventory`, `bartika-jeans/general`.

- لا تضع API Secret في المتصفح أو `NEXT_PUBLIC_*`.

### البريد وSupabase Auth

- صفحة `/forgot-password` وتدفق العودة من رابط الاستعادة منشوران على الدومين الأساسي.
- خدمة البريد الافتراضية أعادت `429 email rate limit exceeded` عند تجاوز حد الإرسال؛ سجل Auth أظهر أيضًا طلب استعادة واحدًا ناجحًا.

## 5. ما هو موجود في التطبيق

### الإدارة والمبيعات
- Next.js 15 / React 19 / TypeScript بواجهة عربية RTL.
- Admin / Manager / Seller وصلاحيات المدير بتفويض Admin.
- إدارة منتجات ومتغيرات متعددة المقاسات والألوان والباركود، مخزون وحركات.
- POS وفواتير وخصومات ودفع Cash / InstaPay / Visa / Mixed.
- RPC بيع ذرية، قراءة الأسعار من DB، أقفال مخزون، وحماية idempotency.
- فواتير شراء متعددة البنود واستلام المخزون وتحديث التكلفة.
- جرد وتسويات باعتماد Admin.
- صور المنتج عبر Cloudinary signed upload route؛ التفعيل الحي متوقف على أسرار الحساب.

### الخزينة والموردون والعملاء
- كل فاتورة بيع مرتبطة بالوردية النقدية المفتوحة وقت البيع.
- قيد فريد يمنع أكثر من وردية مفتوحة للبائع نفسه.
- المصروف العام لا يخصم من أدراج البائعين؛ المصروف النقدي المرتبط يخصم من الوردية المحددة فقط.
- إغلاق الوردية يأخذ في الاعتبار البيع والتحصيل والاستبدال والطلبات الإلكترونية وسداد الموردين المرتبط بدرج محدد.
- ملفات العملاء وسجل الفواتير وحدود ائتمان Admin وتحصيل المستحقات.
- دفتر مستقل لسداد الموردين وكشف حساب المورد.
- الاستبدال مرتبط ببند الفاتورة الأصلية ويحد الكميات المرتجعة ويحدث المخزون ويعالج فرق السعر.

### التقارير والمتجر الإلكتروني
- تقارير مبيعات وأداء مع حماية التكلفة والربح حسب الدور.
- لقطات تكلفة تاريخية على بنود البيع، ويمنع إظهار الربح عند غياب تكلفة موثوقة.
- كتالوج عام في `/shop` وإدارة الطلبات في `/online-orders` للأدمن.
- الطلب يبدأ Unpaid ويحجز المخزون مؤقتًا.
- الكتالوج العام لا يكشف كمية المخزون الفعلية؛ يعرض مؤشرًا بحد أقصى 5.
- حد 3 طلبات لكل هاتف في الساعة وidempotency.
- ينتهي حجز الطلب غير المدفوع بعد 24 ساعة، لكن الطلب ذو الدفع الجزئي يبقى لمراجعة Admin.
- لا توجد بوابة دفع آلية أو تكامل شحن آلي.

## 6. الأمان

- RLS مفعل على جميع جداول `public` الثلاثين.
- توجد تحذيرات عامة على دوال `SECURITY DEFINER` المتاحة للمستخدم المسجل. المراجعة اليدوية للدوال المالية المهمة أظهرت تحققًا داخليًا من الدور النشط أو ملكية الفاتورة/الوردية في الوظائف التي فُحصت.
- دالة `add_expense` ذات الأربع معاملات هي Wrapper تستدعي overload بخمس معاملات، والـoverload الأساسي يفرض `is_admin()`; لم يتم تعطيلها حتى لا تكسر التوافق.
- دوال `get_public_catalog` و`get_public_store_settings` و`create_online_order` مقصودة كواجهات عامة محدودة.
- هذا الفحص ليس بديلًا عن اختبار قبول كامل لكل دور، ويجب إعادة فحص Advisor قبل الإطلاق.
- لم يتم تفعيل Leaked Password Protection بعد.

## 7. ما لم يكتمل بعد

### يحتاج إعدادات وخدمات
1. تحويل GitHub repository إلى Private.
2. إضافة Cloudinary API Key وAPI Secret وتأكيد Folder Mode ثم اختبار رفع حي من Admin.
3. توحيد مصدر شعار BARTIKA مع Cloudinary المعتمد.
4. تفعيل Custom SMTP وحماية كلمات المرور المسربة.
5. رقم الهاتف وعنوان الفرع غير مكتملين في إعدادات المتجر.

### محتوى وتشغيل المحل
1. إدخال المنتجات الحقيقية والمقاسات والألوان والباركود والأسعار والتكلفة.
2. إجراء جرد افتتاحي وإدخال المخزون.
3. رفع صور المنتجات الحقيقية وربطها بالمنتجات.
4. اختبار الطابعة الحرارية والباركود على أجهزة المحل.
5. اختبار أدوار Admin وManager وSeller والمبيعات والخزينة والطلبات على بيانات معتمدة.
6. إعداد نسخة احتياطية مشفرة وتنفيذ استعادة فعلية.

### وظائف مستقبلية لم تعتمد قواعدها أو تكاملاتها
1. الولاء ونقاط العملاء؛ يلزم اعتماد معادلة الكسب والاستبدال والانتهاء.
2. المرتبات والسلف والخصومات والعمولات ومسيرات الرواتب؛ يلزم تحديد قواعد العمولة.
3. تكامل شركات الشحن والبوليصات والتتبع.
4. بوابة دفع آلية أو تحقق آلي من InstaPay/Visa.
5. صفحات حساب العميل وتتبع طلباته.
6. QR ديناميكي ونشر اجتماعي وجدولة وتحليلات رسمية.
7. مزامنة Offline والبيع دون اتصال؛ غير منفذين عمدًا لتفادي البيع المزدوج وتعارض المخزون.
8. اختبار النسخ الاحتياطي والاستعادة على جهاز/قاعدة بديلة.
