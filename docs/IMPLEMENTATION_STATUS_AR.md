## 3. الخدمات الخارجية

### Supabase

- المشروع مستقل وحالته ACTIVE_HEALTHY.
- آخر ترحيل مطبق هو `0041_expire_reservations_on_order_actions`.
- الجداول محمية بـ RLS، وتم إغلاق تنفيذ الدوال الحساسة من anon باستثناء RPCs العامة المقصودة للكتالوج وإنشاء الطلب.
- توجد Edge Function باسم `admin-create-user`، حالتها ACTIVE و`verify_jwt=true`.
- يوجد Advisor تحذيرات على عدد من SECURITY DEFINER functions المتاحة للمستخدم المسجل. يجب اختبارها بأدوار حقيقية ومراجعة صلاحياتها قبل الإنتاج؛ نجاح CI وحده لا يغني عن اختبار صلاحيات DB.
- لم يتم إنشاء مستخدم Admin حتى الآن.

### Cloudinary

- الموجود: مجلدات `bartika-jeans/products`, `bartika-jeans/inventory`, `bartika-jeans/general` داخل الحساب المتصل، والشعار المرفوع تحت `bartika-jeans/general/bartika-brand-logo.webp`.
- الحساب الحالي مشترك؛ هذه المجلدات ليست Product Environment أو حسابًا مستقلًا.
- كود الرفع الموقّع موجود في التطبيق، لكنه يحتاج Cloud Name وAPI Key وAPI Secret وFolder Mode الصحيحين.
- لم تُوفر مفاتيح البيئة المستقلة ولم يُختبر رفع صورة منتج حيًا من الواجهة.
- حساب Cloudinary المتصل أظهر Free plan واستخدامًا قائمًا؛ لا نعتبره مساحة BARTIKA مستقلة.

### Vercel

- لا يوجد مشروع باسم `bartika-jeans` ولا Deploy مسجل.
- محاولات الإنشاء عبر الفريق المتصل والحساب الشخصي أعادت 403 Forbidden.
- لا يوجد Vercel CLI مثبت كبديل في بيئة التنفيذ.
- لا توجد متغيرات بيئة Production أو Preview أو Development ولا رابط نشر.

## 4. ما هو موجود في التطبيق وقاعدة البيانات

### الإدارة والمبيعات
- Next.js 15 / React 19 / TypeScript بواجهة عربية RTL.
- Admin / Manager / Seller وصلاحيات المدير بتفويض Admin.
- إدارة منتجات ومتغيرات متعددة المقاسات والألوان والباركود، مخزون وحركات.
- POS وفواتير وخصومات ودفع Cash / InstaPay / Visa / Mixed.
- RPC بيع ذرية، قراءة الأسعار من DB، أقفال مخزون، وحماية idempotency.
- فواتير شراء متعددة البنود واستلام المخزون وتحديث التكلفة.
- جرد وتسويات باعتماد Admin.
- صور المنتج عبر Cloudinary signed upload route؛ التفعيل الحي متوقف على أسرار الحساب.

### الخزينة والموردون والعملاء
- كل فاتورة بيع مرتبطة بالوردية النقدية المفتوحة وقت البيع.
- قيد فريد يمنع أكثر من وردية مفتوحة للبائع نفسه.
- المصروف العام لا يخصم من أدراج البائعين؛ مصروف Cash المرتبط يخصم من الوردية المحددة فقط.
- إغلاق الوردية يأخذ في الاعتبار البيع والتحصيل اللاحق والاستبدال والطلبات الإلكترونية وسداد الموردين المرتبط بدرج محدد.
- ملفات العملاء وسجل الفواتير وحدود ائتمان Admin وتحصيل المستحقات.
- دفتر مستقل لسداد الموردين وكشف حساب المورد.
- الاستبدال مرتبط ببند الفاتورة الأصلية ويحد الكميات المرتجعة ويحدث المخزون ويعالج فرق السعر.

### التقارير
- تقارير مبيعات وأداء مع حماية التكلفة والربح حسب الدور.
- لقطات تكلفة تاريخية على بنود البيع.
- يمنع إظهار الربح عند وجود بنود لا تتوفر لها تكلفة تاريخية موثوقة.

### المتجر الإلكتروني
- كتالوج عام في `/shop` وإدارة الطلبات في `/online-orders` للأدمن.
- الطلب يبدأ Unpaid ويحجز المخزون مؤقتًا.
- الكتالوج العام لا يكشف كمية المخزون الفعلية؛ يعرض مؤشرًا بحد أقصى 5.
- الطلبات لها idempotency، وحد عام 3 طلبات للهاتف خلال ساعة.
- لا يمكن التسليم قبل اكتمال التحصيل؛ Admin يسجل التحصيل/الرد بعد التحقق اليدوي من Cash أو InstaPay أو Visa.
- بعد التسليم يتحول الطلب إلى فاتورة بيع مرتبطة بالطلب وتُسجل حركات المخزون.
- طلب بلا أي تحصيل ينتهي حجزه بعد 24 ساعة ويُلغى ويُحرر المخزون عند تحديث الكتالوج أو إنشاء طلب جديد أو محاولة Admin تغيير الحالة.
- الطلب ذو الدفع الجزئي لا يُلغى ولا يُرد تلقائيًا؛ يحتاج معالجة Admin موثقة.
- رسوم التوصيل ليست جزءًا من إجمالي المنتجات في الواجهة، وتُحدد عند التواصل.
- لا يوجد تكامل شركات شحن أو بوابة دفع آلية.

## 5. آخر الترحيلات والاختبارات الخاصة بالمتجر

- `0039_restore_order_cost_snapshots_and_phone_throttle`: حفظ snapshots الباركود والتكلفة، idempotency، وقفل الهاتف لمنع تجاوز حد الطلبات.
- `0040_expire_unpaid_online_reservations`: expires_at 24 ساعة وتنظيف الحجوزات من الكتالوج العام.
- `0041_expire_reservations_on_order_actions`: تنفيذ تنظيف الحجوزات قبل إنشاء طلب جديد وقبل تغيير Admin لحالة الطلب.
- اختبار SQL داخل BEGIN/ROLLBACK أثبت: طلب غير مدفوع يبدأ بصفر Paid، لقطات الباركود والتكلفة تُحفظ، تكرار المفتاح لا يحجز مرتين، حد الهاتف يعمل، الحجز المنتهي يحرر الكمية قبل إنشاء طلب جديد، والطلب ذو الدفع الجزئي يظل محجوزًا لمراجعة Admin.
- كل بيانات الاختبار تراجعت بالـROLLBACK، واستعلامات ما بعد الاختبار أثبتت عدم وجود سجلات اختبار متبقية.
- GitHub CI السابق نجح في typecheck/tests/lint/build على دفعات المتجر والطلبات. PR18 قيد CI قبل الدمج.

## 6. ما لم يكتمل بعد

### يحتاج المالك/الخدمة
1. تحويل GitHub repository إلى Private.
2. منح صلاحية Vercel Owner أو Project Create، أو توصيل حساب Vercel مناسب.
3. إنشاء مشروع Vercel وربطه بفرع main وإضافة Supabase env vars.
4. إنشاء/اختيار Cloudinary account أو Product Environment مستقل وتوفير مفاتيحه؛ لا يمكن إنشاء هذه البيئة من إجراءات Cloudinary المتاحة حاليًا.
5. إنشاء أول حساب Admin وتفعيل profile.
6. إدخال بيانات المتجر ورقم الهاتف والعنوان ورسوم التوصيل النهائية.

### محتوى وتشغيل المحل
1. إدخال المنتجات الحقيقية والمقاسات والألوان والباركود والأسعار والتكلفة.
2. جرد افتتاحي وإدخال المخزون.
3. صور ووصف المنتجات؛ لا توجد صور منتجات أو أوصاف فعلية في DB بعد. الموجود شعار العلامة فقط.
4. اختبار رفع الصور من حساب Admin فعلي بعد إعداد Cloudinary.
5. اختبار الطابعة الحرارية وماسح/قارئ الباركود على أجهزة المحل.

### وظائف لم تعتمد قواعدها أو تكاملاتها
1. نظام الولاء ونقاط العملاء؛ طريقة كسب النقاط واستبدالها وانتهائها تحتاج اعتماد Admin.
2. المرتبات والسلف والخصومات والعمولات ومسيرات الرواتب؛ صيغة العمولة لم تحدد.
3. حساب شحن آلي وتكامل شركات الشحن والبوليصات والتتبع.
4. بوابة دفع أو تحقق آلي من InstaPay/Visa.
5. صفحات حساب العميل وتتبع طلباته ذاتيًا.
6. QR ديناميكي، نشر وجدولة اجتماعية وتحليلات من APIs الرسمية.
7. مزامنة Offline وبيع دون اتصال؛ غير منفذين عمدًا لتفادي بيع مزدوج أو تضارب مخزون.
8. النسخ الاحتياطي المشفر والاستعادة على جهاز/قاعدة بديلة؛ لم يختبرا عمليًا.
