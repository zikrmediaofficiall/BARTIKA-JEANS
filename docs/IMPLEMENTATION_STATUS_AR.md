# حالة التنفيذ والفجوات — BARTIKA JEANS

آخر تحديث: 16 نوفمبر 2026. هذه الوثيقة تصف الحالة التي تم التحقق منها مباشرة، وتفصل بين تجهيز البنية وبين اكتمال نظام البيع والمتجر التجاري.

- Supabase الخاص بـ BARTIKA: `BARTIKA-JEANS`، Project Ref: `gnebcwgaahwowxwiqqlj`، Region: `eu-central-1` (Frankfurt)، والحالة `ACTIVE_HEALTHY`.
- مشروع ZIKR ما زال مشروعًا منفصلًا باسم `Zikrofficial` وRef مختلف `zqtssvlvmkzeeyqghqfk`.
- لم تُطبق أي Migration خاصة بـ BARTIKA على قاعدة ZIKR، ولم يُربط مستودع BARTIKA بمشروع Vercel الخاص بـ ZIKR.
- قاعدة BARTIKA فارغة من بيانات التشغيل الحقيقية حتى الآن: لا منتجات أو متغيرات أو مخزون أو فواتير أو ملفات موظفين. يوجد صف إعدادات متجر ابتدائي باسم BARTIKA JEANS / بارتيكا جينز مع مدة استبدال 3 أيام.

## 2. الخدمات الخارجية

### Supabase — تم التجهيز

- تم إنشاء مشروع مستقل وصحي لـ BARTIKA.
- تم تطبيق Migrations من `0001` حتى `0013` على مشروع BARTIKA فقط.
- تم نشر Edge Function باسم `admin-create-user` وحالتها `ACTIVE` مع `verify_jwt=true`.
- تم توليد أنواع TypeScript من مخطط قاعدة BARTIKA واستخدامها في عميل Supabase بالمتصفح والخادم.
- تم التحقق من وجود 23 جدولًا في public، وجميعها مفعّل عليها RLS.
- لم يظهر أي جدول لديه أكثر من سياسة SELECT واحدة بعد تجميع سياسات القراءة.
- لم تعد دوال SECURITY DEFINER قابلة للتنفيذ من دور `anon` بعد Migration 0012 و0013.
- ما زال Supabase Advisor يعرض 14 تحذيرًا عن دوال SECURITY DEFINER المتاحة للمستخدم المسجّل `authenticated`. هذه RPCs مطلوبة للعمليات الذرية، وتفحص داخلها الدور/الملكية/الصلاحية، لكنها تظل تحذيرات تحتاج اختبار اختراق وصلاحيات فعلي بحسابات Admin/Manager/Seller قبل الإنتاج.
- لا يوجد حساب Admin أولي حتى الآن؛ يجب إنشاء مستخدم المالك من Supabase Authentication ثم منحه دور admin بالخطوات الموجودة في `docs/PRODUCTION_SETUP_AR.md`.

### Cloudinary — فصل تنظيمي فقط

- تم إنشاء المجلدات: `bartika-jeans/products` و`bartika-jeans/inventory` و`bartika-jeans/general`.
- تم رفع شعار BARTIKA المرفق إلى `bartika-jeans/general/bartika-brand-logo.webp`، والتحقق من وجوده على Cloudinary؛ رابط HTTPS محفوظ في `store_settings.logo_url`.
- تم دمج الشعار في القائمة الجانبية وصفحة تسجيل الدخول. النسخة المرفوعة WebP بمقاس 192×192، وليست ملف الطباعة الأصلي عالي الدقة.
- كود الرفع الموقّع لصور المنتجات موجود، ويتطلب جلسة Admin، ويدعم JPG/PNG/WebP حتى 10MB.
- مجلد المنتجات لا يحتوي صور منتجات بعد؛ الأصل المتاح حاليًا هو شعار العلامة فقط. لم تُختبر رحلة رفع صورة منتج من واجهة التطبيق بحساب Admin فعلي.
- هذه المجلدات تقع داخل بيئة Cloudinary المتصلة الحالية؛ ليست حسابًا أو Product Environment مستقلًا عن بقية استخدامات الحساب.
- لم تُضف مفاتيح Cloudinary الخاصة ببيئة BARTIKA إلى Runtime بعد. يجب توفير Cloud Name / API Key / API Secret وتحديد نمط المجلدات fixed أو dynamic بدقة.

### Vercel — غير منشأ وغير منشور

- لم يظهر مشروع باسم `bartika-jeans` في قائمة مشاريع Vercel.
- محاولات الإنشاء والربط أعادت `403 Forbidden` بسبب عدم امتلاك الحساب/الفريق المتصل صلاحية إنشاء مشروع.
- لم يتم إعداد Production/Preview/Development environment variables، ولم يحدث Deploy.
- مشروع Vercel الخاص بـ ZIKR لم يُستخدم أو يُعدل. يلزم Owner أو Project Create permission لحساب/فريق Vercel مناسب.

## 3. ما تم تنفيذه في الكود وقاعدة البيانات

- واجهة Next.js 15 / React 19 / TypeScript عربية RTL.
- تسجيل دخول وإطار صلاحيات Admin / Manager / Seller.
- صلاحيات المدير تفويضية وتبدأ دون صلاحيات إضافية.
- حد الخصم أصبح مرتبطًا بملف المستخدم وقابلًا للتهيئة بين 0% و100% مع تحقق قاعدة البيانات.
- RPC البيع ينفذ البيع ذريًا، ويقرأ السعر من قاعدة البيانات، ويقفل صفوف المخزون بترتيب ثابت، ويدعم idempotency والدفع المختلط والجزئي والمتبقي.
- إضافة منتج عبر RPC إداري تنشئ المنتج ومتغيرًا واحدًا وباركودًا ومخزونًا افتتاحيًا وحركة مخزون وسجل تدقيق.
- صفحات/وحدات أولية موجودة لـ POS والمنتجات والمخزون والمشتريات والجرد والفواتير والعملاء والخزينة والموظفين والتقارير والإعدادات.
- دعم رفع صور المنتج إلى Cloudinary موقّع من الخادم، وحفظ image_url وimage_public_id.
- إصلاح حساب إغلاق الخزينة: المصروف العام من خزينة المحل لا يخصم من كل درج بائع؛ المصروف المرتبط بدرج يخصم من الوردية المحددة فقط.
- سجل تدقيق وحركات مخزون وسياسات RLS.
- CI على main نجح في: npm install، typecheck، tests، lint، production build. آخر تشغيل ناجح: [GitHub Actions run 43819279628](https://github.com/zikrofficial-X/BARTIKA-JEANS/actions/runs/43819279628).

## 4. ما لم يكتمل بعد — لا تعتبره ميزة جاهزة

### المتجر الإلكتروني العام
- لا توجد بعد تجربة متجر عامة مكتملة تشمل تصنيفات ومنتجات قابلة للتصفح، تفاصيل منتج، بحث وفلاتر، سلة، Checkout، طلبات، تتبع طلب أو حساب عميل.
- لا يوجد تكامل شحن أو حساب أسعار تغطية/شحن أو بوليصات أو تحديث حالات.
- لا توجد آلية حجز مخزون لطلبات الويب مع مهلة انتهاء الحجز أو سياسة إلغاء.

### المنتجات والمخزون والمشتريات
- شاشة إنشاء المنتج تنشئ متغيرًا واحدًا فقط؛ إدارة عدة مقاسات وألوان وباركود لكل متغير تحتاج استكمال واجهة الإدارة.
- لا توجد بعد أسعار جملة وشرائح كمية ولا معرض صور متعدد أو صور لكل لون.
- شاشة المشتريات الحالية تسجل متغيرًا واحدًا لكل عملية بالرغم من أن نموذج قاعدة البيانات يسمح ببنود شراء متعددة؛ يلزم إكمال واجهة الفاتورة متعددة البنود وكشف حساب المورد.
- لا توجد بيانات منتجات أو مخزون حقيقي؛ يلزم إدخالها بعد الجرد الافتتاحي.

### الاستبدال والعملاء والذمم
- مسار الاستبدال الحالي شاشة توضيحية/غير مفعلة، وليس دورة استبدال فعلية مع الفاتورة الأصلية وفروق السعر وحركات المخزون.
- ملف العميل وسجل الشراء والنقاط والولاء والحد الائتماني والتحصيلات والذمم تحتاج استكمالًا.
- سياسة 3 أيام لا يجوز استخدامها للانتقاص من حقوق المستهلك القانونية في السلع المعيبة أو غير المطابقة.

### المالية والموظفون والتقارير
- التقارير الحالية أساسية وتعرض آخر الفواتير/إجمالي المبيعات؛ لم يكتمل حساب COGS التاريخي وصافي الربح والمرتجعات والمصروفات والذمم.
- إدارة الموظفين تغطي إنشاء بائع/مدير وحد الخصم وصلاحيات المدير؛ المرتبات والسلف والخصومات والعمولات والأهداف ومسيرات الرواتب غير مكتملة.
- صيغة العمولة لم تُحسم بعد.

### العمل دون إنترنت والنسخ الاحتياطي
- PWA يخزن الغلاف الثابت وصفحة Offline فقط. لا توجد مبيعات Offline ولا طابور مزامنة idempotent ولا تسوية تعارضات مخزون بين أجهزة منفصلة.
- لا يوجد اختبار مثبت لنسخ احتياطي مشفر واستعادة كاملة على جهاز/قاعدة بديلة.
- لا يجوز إعلان البيع دون اتصال جاهزًا قبل اختبارات فقد/تكرار/تزامن وتضارب المخزون.

### الهوية والمحتوى والتكاملات
- الشعار الأصلي الذي أرفقه المالك مدمج حاليًا في التنقل وتسجيل الدخول عبر صورة Cloudinary؛ يلزم لاحقًا إضافة ملف Vector/عالي الدقة إذا كان مطلوبًا للطباعة والهوية الرسمية. لم تُرفع صور منتجات بعد.
- بيانات التواصل وروابط Facebook/Instagram/TikTok/WhatsApp وInstaPay موثقة في وثيقة الخطة، لكنها لم تتحول بعد إلى صفحات متجر/QR أو تدفق تحقق دفع.
- لا توجد APIs نشر اجتماعي أو جدولة أو تحليلات مرتبطة فعليًا.
- الطابعة الحرارية والماسح والباركود لم تُختبر على أجهزة المحل الحقيقية.

## 5. اختبارات القبول المتبقية قبل فتح البيع

1. إنشاء أول Admin، ثم إنشاء حسابات منفصلة لـ Manager وSeller واختبار كل صلاحية في DB وAPI والواجهة.
2. اختبار أن البائع لا يمكنه قراءة تكلفة/جملة/ربح حتى عبر استدعاءات REST مباشرة.
3. اختبار بيع متزامن على آخر قطعة، وإعادة إرسال نفس idempotency key، والتأكد من عدم تكرار الفاتورة أو حركة المخزون.
4. اختبار دفع Cash/InstaPay/Visa ومزيج الدفع والآجل مع إجمالي متبقٍ مضبوط.
5. اختبار ورديتين متزامنتين، ومصروف عام، ومصروف مرتبط بدرج واحد؛ لا يخصم المصروف مرتين.
6. اختبار شراء متعدد البنود، استلام، جرد، اعتماد تسوية، استبدال ومرتجع.
7. اختبار صور Cloudinary الفعلية والمجلد الصحيح والصلاحيات وحدود الحجم.
8. اختبار نسخ احتياطي واستعادة، ثم اختبار الأجهزة والطابعة والماسح.
9. إنشاء Vercel project مستقل، إعداد الأسرار، Deploy Preview ثم Production، واختبار الموقع من خارج شبكة المحل.
10. بناء واختبار المتجر العام والشحن والحجز قبل الإعلان عن وجود متجر إلكتروني عامل.
