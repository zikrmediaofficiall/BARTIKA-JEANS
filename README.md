## الوظائف الموجودة

- تسجيل دخول وأدوار Admin / Manager / Seller مع صلاحيات Manager يمنحها Admin.
- لوحة إدارة، كتالوج منتجات، أصناف متعددة المقاسات والألوان، SKU وباركود ومخزون.
- POS وفواتير بيع وخصومات ومدفوعات Cash / InstaPay / Visa / Mixed.
- ربط البيع بالوردية النقدية الصحيحة ومنع فتح أكثر من درج مفتوح للبائع نفسه.
- جرد ومشتريات متعددة البنود وحركات مخزون.
- دفتر منفصل لسداد الموردين وكشف حساب المورد.
- ملفات العملاء، حدود ائتمان، أرصدة مستحقة وتحصيل لاحق.
- استبدال ومرتجعات مرتبطة ببند الفاتورة الأصلية مع تسوية فرق السعر.
- تقارير مالية ولقطات تكلفة تاريخية؛ لا يعرض النظام الربح عندما تكون بيانات التكلفة ناقصة.
- متجر عام في `/shop` ولوحة إدارة الطلبات `/online-orders` للأدمن فقط.
- صفحة روابط عامة `/links` ومركز QR إداري `/qr`، مع QR على الفواتير.
- مولد باركود Code 128 وملصقات قابلة للطباعة من `/barcodes`.
- إدارة شركات الشحن ومناطق ورسوم التوصيل من `/shipping`، مع حساب رسوم الشحن على الخادم واختيار تفضيل الدفع في المتجر.
- PWA وغلاف Offline؛ لا يدعم البيع أو مزامنة الفواتير دون اتصال.

## المتجر العام والطلبات

- يعرض الكتالوج المنتجات النشطة وسعر البيع والصورة والمقاسات والألوان المتاحة.
- مؤشر المخزون العام محدود إلى 0–5 ولا يكشف الكمية الفعلية للفرع.
- الطلب الإلكتروني يبدأ Unpaid مع حجز مؤقت للمقاسات، ولا يقوم الموقع بتحصيل InstaPay أو Visa آليًا.
- يجب على Admin التحقق من استلام النقدية أو التحويل ثم تسجيل التحصيل داخل لوحة الطلبات. لا يسمح النظام بتسليم الطلب قبل اكتمال دفع قيمته.
- بعد اكتمال التحصيل والتسليم تتحول الطلبات إلى فاتورة بيع مرتبطة بالطلب، مع تسجيل حركات المخزون ولقطة تكلفة الصنف إن كانت متاحة.
- رسوم التوصيل غير مضافة إلى إجمالي المنتجات في صفحة المتجر؛ يؤكدها المحل عند التواصل مع العميل.
- الطلب الذي لم يُسجل عليه أي تحصيل ينتهي حجزه بعد 24 ساعة ويُلغى ويُحرر المخزون عند تحديث الكتالوج أو إنشاء طلب جديد أو محاولة Admin تغيير حالة الطلب.
- الطلب ذو التحصيل الجزئي لا يُلغى آليًا ولا يُرد مبلغه آليًا؛ يتطلب معالجة Admin موثقة.
- الحد العام الحالي ثلاثة طلبات من رقم الهاتف في الساعة، ومفتاح idempotency يمنع تكرار الطلب عند إعادة الإرسال.

## Supabase والترحيلات

الترحيلات من `0001` حتى `0045` مطبقة على مشروع BARTIKA فقط. سجل Supabase البعيد يستخدم إصدارات زمنية من 14 رقمًا؛ يجب أن تتطابق بادئة كل ملف محلي مع الإصدار البعيد بصيغة `<timestamp>_<name>.sql`. تمت مواءمة أسماء الملفات مع الإصدارات المسجلة دون تعديل سجل قاعدة البيانات أو إعادة تنفيذ SQL المطبق.

يوجد إصداران تاريخيان `20261116074349` و`20261116074500` يحملان الاسم `0016_admin_financial_profit_reports`، وتم التحقق أن محتوى SQL لهما متطابق (MD5 واحد). يحتفظ المستودع بملفين مطابقين لهذين الإصدارين التاريخيين لضمان تطابق التاريخ المحلي والبعيد.

لا تستخدم أيًا من ترحيلات BARTIKA على مشروع ZIKR.

## Cloudinary

- الحساب المتصل: `lnsnp6km`.
- الشعار الرسمي المرفوع إلى `bartika-jeans/general` تحت Public ID `bartika-brand-logo-2026`: https://res.cloudinary.com/lnsnp6km/image/upload/v1794847704/bartika-brand-logo-2026.webp.
- تم ربط `public.store_settings.logo_url` بالشعار الجديد، وتوحيد صور الدخول واللوحة وبيانات PWA على الأصل نفسه.
- تم تأكيد وجود `CLOUDINARY_API_KEY` و`CLOUDINARY_API_SECRET` كقيم مشفرة في Production وPreview وDevelopment، مع `CLOUDINARY_FOLDER_MODE=dynamic`.
- كود الرفع الموقّع موجود في `src/app/api/cloudinary/signature/route.ts` ويتطلب Admin.
- لا تضع API Secret في GitHub أو في أي متغير `NEXT_PUBLIC_*`.

## البريد وتسجيل الدخول

- صفحة `/login` تحتوي على رابط استعادة كلمة المرور، وصفحة `/forgot-password` متاحة على الدومين الأساسي.
- تدفق استعادة كلمة المرور مدمج في `main`، ويعيد المستخدم إلى الدومين الأساسي.
- خدمة البريد الافتراضية في Supabase وصلت إلى حد الإرسال في اختبار الاستعادة (429 / `email rate limit exceeded`). يلزم إعداد Custom SMTP لاستخدام موثوق، وعدم تعطيل تأكيد البريد كحل بديل.
- Advisor من Supabase أظهر أن Leaked Password Protection غير مفعّل؛ يجب تفعيله قبل الإطلاق التجاري.

## الأمان والجاهزية

- جداول `public` الثلاثون عليها RLS.
- بعض RPCs تستخدم `SECURITY DEFINER` مع صلاحيات تنفيذ للمستخدم المسجل. تمت مراجعة مجموعة من الدوال المالية والإدارية وتبين وجود تحقق داخلي من الدور النشط أو ملكية السجل، بينما دوال الكتالوج وإعدادات المتجر وطلب الشراء العام مقصودة كواجهات عامة محدودة. تظل تحذيرات Advisor قائمة وتتطلب اختبارًا شاملًا للأدوار قبل الإطلاق.
- لا توجد أخطاء Runtime حديثة في آخر نافذة فحص Vercel (30 دقيقة)، لكن لا يغني ذلك عن اختبار تشغيل كامل بحسابات Admin / Manager / Seller.
- يوجد إعداد متجر افتراضي باسم BARTIKA وروابط تواصل ووسيلة InstaPay، لكن رقم الهاتف والعنوان غير مدخلين بعد.

## بوابات ما قبل التشغيل التجاري

1. تحويل مستودع GitHub إلى Private.
2. إضافة Cloudinary API Key وAPI Secret وتأكيد Folder Mode، ثم اختبار رفع منتج من حساب Admin end-to-end.
3. تفعيل SMTP مخصص وLeaked Password Protection في Supabase Auth.
4. استكمال رقم الهاتف وعنوان الفرع وسياسات المتجر بعد اعتماد المالك.
5. إدخال المنتجات الفعلية والمقاسات والألوان والباركود والأسعار والتكلفة، ثم تنفيذ الجرد الافتتاحي.
6. اختبار Admin / Manager / Seller، البيع والتحصيل والخزينة والاستبدال والطلبات الإلكترونية.
7. اختبار الطابعة الحرارية والباركود على أجهزة المحل.
8. إعداد نسخة احتياطية مشفرة وتنفيذ استعادة تجريبية.
9. لا يوجد بيع Offline آمن أو مزامنة معاملات، ولا تكامل بوابة دفع أو شركة شحن في هذا الإصدار.
